# 三模式采集链路与包装 OCR 设计

## 1. 目标

在现有的 RV101 实时预览和高清 JPEG 上传能力上，建立统一的采集流程：

- 低分辨率预览帧持续用于手势和场景判断；
- 高清照片只在满足触发条件时请求眼镜拍摄；
- 餐食、包装/配料表走不同的触发路径；
- 图片进入原有食品识别、饮食记录和后续 OCR 流程前，保留质量检查与用户确认。

本设计不改变现有网络链路：RV101 与手机处于同一 Wi-Fi 或手机热点，眼镜通过 WebRTC 传预览、通过 HTTP 上传 JPEG。

## 2. 核心原则

### 2.1 眼镜端只做采集和传输

眼镜端保持以下职责：

1. Camera2 持续输出 `640x480` 预览帧；
2. 将预览帧推送为 WebRTC 实时画面；
3. 低频向手机发送 JPEG 候选帧；
4. 收到手机 `capture` 指令后拍摄并上传高清 JPEG；
5. 不在眼镜端部署食品分类、OCR 或热量模型。

### 2.2 手机端负责判断与调度

手机端负责：

1. 手势识别；
2. 餐食二分类模型；
3. 三种模式和进餐状态维护；
4. 高清拍摄调度、延迟、冷却、重拍；
5. 包装/配料表 OCR、结构化解析和用户确认；
6. 调用既有食品识别、营养分析和饮食记录模块。

### 2.3 一条高清拍摄入口

手势、App 按钮、自动场景判断都不能各自直接控制相机。它们统一向手机端 `CaptureCoordinator` 提交任务，由该调度器通过现有 WebRTC DataChannel 发送：

```json
{
  "type": "capture",
  "trigger": "meal_before"
}
```

这样可以保证同一时刻只拍一张照片，并处理优先级、延迟和冷却。

## 3. 三种采集模式

| 模式 | 触发来源 | 高清拍摄策略 | 适用内容 |
|---|---|---|---|
| 手动模式 | App 按钮、明确手势 | 触发后延迟拍一张 | 包装、配料表、用户主动拍摄 |
| 自动模式 | 手机端食品二分类 | 稳定餐食候选满足条件后自动拍摄 | 餐食图片 |
| 混合模式 | 手势、App 按钮、食品二分类 | 自动采集开启，但明确用户指令优先 | 日常进餐采集 |

### 3.1 手动模式

用于用户有明确拍摄意图的场景：

- App 中点击“眼镜抓拍”；
- OK 手势：包装、配料表或营养成分表；
- 后续可扩展其他明确手势。

默认行为：确认触发后等待 `2 秒`，让手离开画面，再请求高清 JPEG。默认不依赖食品二分类结果。

### 3.2 自动模式

自动模式只自动采集餐食，不自动拍包装、货架、广告或配料表。

```text
低清候选帧
  -> 手机端 food_scene / not_food_scene 二分类
  -> 连续命中 food_scene
  -> 画面质量与重复度检查
  -> 请求高清餐食图
```

建议的初始阈值：

- 连续 `2` 帧 `food_scene`；
- 每帧置信度不低于 `0.80`；
- 距离上一次自动高清拍摄至少 `8 秒`；
- 同一进餐时段内，若与最近有效图高度重复则不拍；
- 自动模式关闭、离开实时预览页或用户停止采集后，不再触发。

自动模式可以在 `IDLE` 状态下由稳定的 `food_scene` 候选直接启动一次
`meal_before` 高清抓拍；如果当前已经处于 `EATING` 状态，则后续候选标记为
`meal_during`。自动模式仍然不会触发包装或配料表采集。

### 3.3 混合模式

混合模式同时启用自动采集和显式用户触发，优先级如下：

```text
握拳 / 取消
  > App 立即抓拍、OK 包装手势或模式切换
  > 张开手掌开始进食
  > 食品二分类自动任务
```

若正在拍照或处于冷却期，低优先级自动任务直接丢弃；明确手势任务可排队执行。

## 4. 手势与进餐状态机

手机端统一维护 OK、张开手掌和握拳手势，并通过连续多帧一致结果切换进餐状态。
自动候选也可以从 `IDLE` 进入餐食采集路径；显式用户停止或取消始终拥有更高优先级。

```text
IDLE
  -> Stable food_scene candidate or Open Palm confirmed
  -> WAITING_BEFORE_CAPTURE
  -> EATING
  -> FIST confirmed
  -> WAITING_AFTER_CAPTURE
  -> IDLE
```

### 4.1 张开手掌：开始进食

连续识别 `2-3` 个张开手掌结果后：

1. 进入 `WAITING_BEFORE_CAPTURE`；
2. 等待 `2-3 秒`，避免手遮挡餐食；
3. 请求高清拍摄；
4. 上传图片时写入：

```json
{
  "trigger": "open_palm",
  "scene": "meal_before",
  "mealSessionId": "generated-id"
}
```

5. 成功或失败后进入 `EATING`。

### 4.2 自动餐食采集

在 `IDLE` 状态下，自动模式或混合模式对稳定的 `food_scene` 候选请求
`meal_before` 高清照片；成功后进入 `EATING`。在 `EATING` 状态下，后续候选
才请求 `meal_during` 高清照片。两种情况下都必须经过质量、重复度、冷却和用户审阅逻辑。
进食中的后续图片标记为 `meal_during`；如果候选从 `IDLE` 启动事件，则将该字段写为
`meal_before`。进食中的元数据示例如下：

```json
{
  "trigger": "auto_food_scene",
  "scene": "meal_during",
  "mealSessionId": "generated-id"
}
```

自动场景识别由手机端食品二分类模块提供；当该模块或实时预览不可用时，自动任务
应被禁用并明确显示状态，不得伪装为已开启自动拍摄。

### 4.3 握拳：结束进食

连续识别 `2-3` 个握拳结果后：

1. 取消未执行的自动拍摄任务；
2. 等待 `2-3 秒`，让手离开画面；
3. 请求高清拍摄；
4. 上传图片时写入：

```json
{
  "trigger": "fist",
  "scene": "meal_after",
  "mealSessionId": "generated-id"
}
```

5. 结束本次 `mealSessionId` 对应的进餐状态。

若没有检测到握拳，系统最多只能把该时段最后一张有效餐食图标记为 `meal_after_candidate`，并要求用户在手机端确认。不能直接断定用户已结束进餐。

## 5. 自动高清拍摄的质量控制

拍摄任务由 `CaptureCoordinator` 执行，建议参数可配置：

| 参数 | 初始值 | 说明 |
|---|---:|---|
| `captureDelayMs` | 2000 ms | 手势或场景触发到拍摄之间的等待 |
| `autoCooldownMs` | 8000 ms | 两次自动餐食拍摄最小间隔 |
| `manualCooldownMs` | 3000 ms | 两次明确手势拍摄最小间隔 |
| `maxRetakeCount` | 2 | 图片质量不合格时的最大重拍次数 |
| `foodConfidenceThreshold` | 0.80 | 自动二分类阈值 |
| `foodStableFrames` | 2 | 自动触发所需连续命中次数 |

收到高清 JPEG 后，手机端应检查：

1. 是否是有效 JPEG、尺寸是否符合预期；
2. 是否过暗或严重模糊；
3. 食物主体是否明显脱离画面；
4. 是否与最近一张同一餐次图片高度重复。

不合格时允许短间隔重拍。超过最大重拍次数后保留错误状态，不应无限拍摄和上传。

## 6. 包装与配料表 OCR 链路

包装/配料表不通过自动模式拍摄，避免经过货架时误采集商品。

```text
OK 手势或 App 按钮
  -> 延迟等待手离开
  -> 高清 JPEG
  -> 图片方向和清晰度检查
  -> OCR
  -> 结构化解析
  -> 用户确认
  -> 保存为食品详情或风险信息
```

### 6.1 图片标记

```json
{
  "trigger": "ok_gesture",
  "scene": "ingredient_label",
  "mealSessionId": "optional-id"
}
```

### 6.2 OCR 第一版范围

第一版至少完成：

- 显示高清原图；
- 显示 OCR 原始文字；
- 提取配料文本；
- 提取能量、蛋白质、脂肪、碳水化合物、钠；
- 标记字段缺失、OCR 失败和低置信度结果；
- 允许用户修改或确认后再保存。

结构化结果示例：

```json
{
  "ingredients": ["小麦粉", "白砂糖", "植物油", "食用盐"],
  "energyKj": 1850,
  "proteinG": 6.2,
  "fatG": 18.5,
  "carbohydrateG": 62.4,
  "sodiumMg": 420,
  "ocrConfidence": 0.86
}
```

OCR 输出不能直接等价为用户已经摄入该食品，也不能在未确认的情况下直接写入饮食记录。

## 7. 模块划分

### 7.1 张同学：模式、状态机、调度和 OCR

负责手机端：

- `CaptureCoordinator`；
- 手动、自动、混合模式选择和页面状态；
- 张开手掌开始进食、握拳结束进食；
- `meal_before`、`meal_during`、`meal_after` metadata；
- 延迟、冷却、重拍、取消逻辑；
- OK 手势后的包装/配料表拍摄；
- OCR 调用、结构化解析和确认页面。

### 7.2 赵同学：食品二分类模型

负责提供手机端轻量模型：

```text
输入：低清 JPEG
输出：food_scene / not_food_scene + confidence
格式：TFLite
```

需同时提供类别映射、输入尺寸、归一化方式、建议阈值、模型大小、单张推理耗时和测试集指标。

### 7.3 集成负责人：模型接入与真机联调

负责将模型输出接入 `CaptureCoordinator`：

```text
EATING
  -> 连续 food_scene
  -> 非重复且不在冷却期
  -> 提交 meal_during 高清拍摄任务
```

## 8. 当前版本与后续验证

当前已具备：

- 眼镜 Camera2 预览；
- WebRTC 手机实时预览；
- 低频 JPEG 上报；
- OK、张开手掌和握拳识别；
- 手机按钮请求眼镜高清拍摄；
- 高清 JPEG 上传至手机；
- 手动、自动和混合模式页面与状态机；
- 手机端食品二分类、自动餐食候选和自动高清拍摄；
- 图片质量检查、重复过滤、冷却和有限重拍；
- 包装 OCR、字段结构化和用户确认页面。

当前已完成以下闭环验证：

```text
张开手掌
  -> meal_before 高清图
握拳
  -> meal_after 高清图
OK
  -> ingredient_label 高清图
  -> OCR 原始文本与字段解析
```

自动模式和混合模式还验证了从 `IDLE` 餐食候选启动 `meal_before`，以及进食状态中
由稳定 `food_scene` 候选触发 `meal_during` 的路径。包装采集仍始终需要 OK 手势
或 App 的显式命令。
